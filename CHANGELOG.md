# Changelog Contribution Guide

This document serves as the official record of our project's evolution. To keep it organized, readable, and useful, the entire team must follow these **guiding principles**:

### 📋 Golden Rules
1. **Changelogs are for humans, not machines:** Write clearly and understandably. Avoid raw commit messages like `"fix: bug"` or internal codes without context.
2. **One entry per version:** Every time a version is released, it must have its own section.
3. **Reverse chronological order:** The most recent version **always** comes first (at the top).
4. **Mandatory dates:** Each version must include its release date in `YYYY-MM-DD` format.
5. **Semantic Versioning (SemVer):** We follow the `MAJOR.MINOR.PATCH` format (e.g., `1.4.2`).

### 🛠️ Types of Changes (Categories)
When adding a line to the log, you must strictly classify it into one of these sections:
*   `Added`: For new features.
*   `Changed`: For changes in existing functionality.
*   `Deprecated`: For soon-to-be removed features.
*   `Removed`: For now removed features.
*   `Fixed`: For any bug fixes.
*   `Security`: In case of vulnerabilities or security patches.
